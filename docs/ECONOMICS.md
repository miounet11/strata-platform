# 本地 LLM 推理的经济学：一个可复现的成本模型

> 技术报告 · stratat.com · 数据快照 2026-10-07
>
> 本文档描述 `apps/www/src/lib/benchmarks.ts` 中 `computeEconomics()` 的实际计算过程，
> 并给出该模型在 28 台实测配置上的分布结果与敏感性分析。所有数字均可用仓库内数据复现。

## 摘要

本文提出一个用于比较「本地自建推理」与「按量调用 API」的两项核心指标：

- **本地单位成本** `localCostPerMM`（美元 / 百万 token）：把电力与硬件折旧摊到吞吐量上；
- **回本周期** `breakEvenDays`（天）：硬件总价 ÷ 每日相对 API 的净节省。

在 28 台有完整实测数据的配置上，本地单位成本中位数 **$0.097/M tok**，四分位区间 **$0.063–0.123**，
而同期 API 混合价格为 **$0.154/M tok**。回本周期中位数 **814 天**，最省的配置约 **390 天**。

结论分两层，二者不可互相替代：

1. **回本周期**的分子确实是硬件总价，因此它**随显卡价格线性变化**；
2. 但在价格之外，**日活跃小时数**的杠杆远大于价格差异 —— 同一台 RTX 4090，
   24h 满载回本 433 天，降到 4h/天变为 2599 天（约 6 倍），
   而整机价从 \$2380 到 \$8500（约 3.6 倍）才产生可比量级的影响。

所以准确的说法是：**在给定价格区间内，利用率比选哪张卡更能决定回本快慢**，
而不是「盈亏平衡不取决于显卡价格」。

## 1. 模型

### 1.1 吞吐能力

模型采用**单流顺序混合**假设：一个请求的读取阶段与生成阶段串行执行，不重叠。

设读取占比为 $r$（默认 0.9），单卡读取速率为 $t_r$、生成速率为 $t_w$（token/s），
则每个 token 的平均耗时为

$$
s = \frac{r}{t_r} + \frac{1-r}{t_w}
$$

日活跃小时数为 $h$ 时，日吞吐为

$$
C = \frac{h \cdot 3600}{s \cdot 10^6} \quad \text{(M tok/day)}
$$

这一项是该模型最脆弱也最关键的部分。真实的批处理与投机解码会让吞吐显著高于串行估计，
而并发下的显存换页会显著低于它。因此 $C$ 应被理解为**单用户交互场景的下界估计**。

**边界条件**：$h \le 0$、$t_r \le 0$ 或 $t_w \le 0$ 时上式无定义，实现中返回 `null`
而非 0 或 ∞（见 `apps/www/src/lib/benchmarks.ts:58` 的 `hours > 0 && readRate > 0 && writeRate > 0` 守卫）。
下游所有依赖 $C$ 的指标（单位成本、API 价值、回本周期）随之整体为 `null`，
避免把"无法计算"渲染成"成本为零"。同理，$r$ 被钳制在 $[0,1]$，
$L$ 的下限取 0.1 年，防止除零。

### 1.2 日成本

$$
E = \frac{P}{1000} \cdot h \cdot p_e \qquad \text{(电费, } P\text{ 为整机功耗 W, } p_e \text{ 为电价 \$/kWh)}
$$

$$
H = \frac{\text{rigTotal}}{L \cdot 365} \qquad \text{(硬件折旧, } L \text{ 为折旧年限, 默认 5 年)}
$$

### 1.3 本地单位成本

$$
\text{localCostPerMM} = \frac{E + H}{C}
$$

注意分子**不含**机箱、主板、电源之外的人工与运维成本。这是有意的取舍：把可复现的硬件与电费
单独列出，运维成本交由使用者自行叠加，避免把不可验证的数字混入模型。

### 1.4 回本周期

先计算同等 token 量在 API 上的价值。混合 API 单价为

$$
b = r \cdot p_{\text{read}} + (1-r) \cdot p_{\text{write}}
$$

默认 $p_{\text{read}} = \$0.10/M$、$p_{\text{write}} = \$0.64/M$、$r = 0.9$，得 $b = \$0.154/M$。

$$
\text{breakEvenDays} = \frac{\text{rigTotal}}{C \cdot b - E}
$$

当分母不为正（电费超过 API 等价价值）时该指标无定义，模型返回 `null` 而非一个误导性的巨大数字。

### 2.1 单位成本最低的六台配置

| 配置 | $/M tok | 整机价 | 生成速率 | 回本天数 | 证据 |
| --- | --- | --- | --- | --- | --- |
| RTX 4090 | 0.056 | $4199 | 109.3 tok/s | 434 | median |
| RTX 5080 | 0.058 | $2800 | 80.7 tok/s | 393 | median |
| RTX 5070 Ti | 0.060 | $2380 | 71.1 tok/s | 403 | median |
| RTX 3090 | 0.060 | $2700 | 86.5 tok/s | 410 | median |
| RTX 4070 Ti SUPER 16GB | 0.061 | $2140 | 72.0 tok/s | 399 | median |
| RTX 5090 | 0.062 | $8500 | 168.4 tok/s | 558 | median |

值得注意的是 **RTX 4090 单位成本最低，但回本并非最快**；RTX 5080 虽然 $/M 略高，
却因为整机价更低而回本更快（393 vs 434 天）。这说明「单位成本」与「回本速度」是两个
不可互相替代的指标，任何用单一排名回答"值不值"的榜单都在隐藏这一取舍。

> **口径说明**：本节表格中的 `回本天数` 取自数据文件的存量字段（`breakEvenDays`），
> 而第 3 节敏感性分析按当前 `defaults` 现算。两者在 13/28 台配置上相差 1 天
> （例如 RTX 4090：存量 434，重算 433），原因是数据快照生成时参数与当前 `defaults`
> 存在细微差异。正文引用时以各自来源为准，不混用。

### 2.2 单位成本最高的四台配置

| 配置 | $/M tok | 整机价 | 回本天数 |
| --- | --- | --- | --- |
| Mac Studio M5 Max 128 GB | 0.188 | $5399 | 2349 |
| Mac mini M5 Pro 64 GB | 0.207 | $2899 | 2691 |
| Mac Studio M4 Max 128 GB | 0.241 | $6500 | 3111 |
| Mac Studio M3 Ultra 512 GB | 0.548 | $9499 | 15577 |

统一内存机型在此模型下回报显著更差，原因是生成速率低（模型按单流串行估计）而整机价高。
这一结果**不**意味着统一内存架构不受欢迎 —— 它们的价值在于大显存可承载的模型规模，
而模型规模并未进入本成本公式。这是模型明确的适用边界。

## 3. 敏感性分析（RTX 4090，其余参数取默认）

### 3.1 日活跃小时数（影响最大）

| h/天 | 日吞吐 (M tok) | $/M tok | 回本天数 |
| --- | --- | --- | --- |
| 1 | 3.2 | 0.755 | 10397 |
| 2 | 6.3 | 0.390 | 5199 |
| 4 | 12.6 | 0.208 | 2599 |
| 8 | 25.3 | 0.117 | 1300 |
| 12 | 37.9 | 0.087 | 866 |
| 24 | 75.8 | 0.056 | 433 |

$h$ 同时进入分子（电费）与分母（吞吐），但分母线性增长而折旧项不变，因此**利用率是
唯一能把回本周期从十年压到一年量级的参数**。这也是本模型给出的最强实践建议：
先确定设备能达到的日利用率，再讨论硬件选型。

### 3.2 电价

| $/kWh | $/M tok | 回本天数 |
| --- | --- | --- |
| 0.05 | 0.039 | 381 |
| 0.10 | 0.048 | 406 |
| 0.15 | 0.056 | 433 |
| 0.25 | 0.074 | 502 |
| 0.40 | 0.100 | 657 |

电价从 \$0.05 涨到 \$0.40（8 倍），回本周期仅增加 72%。在 24h 满载下，**电费不是主导项，
硬件折旧才是**；只有在低利用率时二者的相对权重才会改变。

### 3.3 读写比

| 读取占比 | 日吞吐 (M tok) | $/M tok | 回本天数 |
| --- | --- | --- | --- |
| 50% | 18.4 | 0.233 | 871 |
| 70% | 29.6 | 0.145 | 727 |
| 90% | 75.8 | 0.056 | 433 |
| 95% | 124.3 | 0.034 | 304 |
| 99% | 254.9 | 0.017 | 169 |

读取速率约为生成速率的 36.6 倍（RTX 4090：4000 / 109.3），所以读写比对结果的影响
接近线性放大。**长上下文、少生成的场景（如文档问答）本地部署优势最大**；
而高生成占比的写作类场景优势明显减弱。

## 4. 模型的已知局限

1. **单流假设**：未建模连续批处理。真实服务多用户时 $C$ 会显著上升，本地成本相应下降。
2. **吞吐线性外推**：长时间满载的热降频、显存带宽饱和均未建模。
3. **电价与折旧为常数**：未计入峰谷电价、二手残值、硬件故障率。
4. **API 价格静态**：$p_{\text{read}}$、$p_{\text{write}}$ 是快照值，API 降价的频率高于硬件。
5. **不含模型质量差异**：本地可跑的量化模型与顶级闭源 API 的能力差距未量化，
   而这一项在实践中常常是真正的决策因素。
6. **统一内存机型被低估**：大显存带来的"能跑"能力无法进入成本公式。

因此本模型只回答一个窄问题：**在给定吞吐假设下，硬件与电费折合每百万 token 多少钱**。
它不回答"该不该本地部署"，只把那个问题里可计算的部分算清楚。

## 5. 复现

```bash
# 由数据与模型直接得出本文全部数字
node -e '
const b = require("./apps/www/src/data/benchmarks.json");
const rows = b.rigs.filter(r => r.localCostPerMM != null)
                   .sort((a, c) => a.localCostPerMM - c.localCostPerMM);
const q = (a, p) => { const s=[...a].sort((x,y)=>x-y); return s[Math.floor(p*(s.length-1))]; };
const lc = rows.map(r => r.localCostPerMM);
console.log([0,.25,.5,.75,1].map(p => q(lc,p).toFixed(3)).join(" / "));
'
```

公式实现见 `apps/www/src/lib/benchmarks.ts:50`（`computeEconomics`）；
参数默认值见 `apps/www/src/data/benchmarks.json` 的 `defaults` 字段；
页面呈现见 `apps/www/src/app/[locale]/method/page.tsx`。
